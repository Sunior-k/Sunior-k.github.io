Background

감사 일기 앱이 해결하려 한 것

감사 일기는 지속하기 어렵습니다. 기록에 대한 즉각적인 피드백이 없기 때문입니다. Clody는 일기를 쓴 사용자에게 AI 로디가 응원의 답장을 보내는 피드백 루프를 설계했습니다.

첫 일기는 1분 이내에 답장이 옵니다. 그 이후부터는 12시간 후에 받을 수 있습니다.
처음 경험이 서비스의 인상을 결정하기 때문에, 첫 응답을 빠르게 제공하는 것을 의도했습니다.

일기 응답을 처음 열람하면 클로버를 획득하며, 보상형 광고를 시청해 추가 보상을 받을 수 있습니다. 임시 저장 기능으로 작성 중인 일기를 잃지 않도록 했고, 인앱 업데이트로 항상 최신 버전을 유도했습니다.

Technical Decisions

왜 그 기술을 선택했는가

왜 JWT 토큰 재발급에 Mutex를 썼는가

AccessToken이 만료된 상태에서 다수의 API 요청이 동시에 발생하면, 각각의 요청이 토큰 재발급 로직을 별도로 수행해 충돌이 발생했습니다. 재발급 API가 중복 호출되면서 발급이 실패하거나 예기치 않은 동작이 생겼습니다.

AS-IS

여러 요청이 동시에 401을 받으면 각자 재발급을 시도합니다.
토큰 충돌로 재발급 실패가 간헐적으로 발생합니다.

TO-BE

Mutex로 재발급을 직렬화합니다.
Deferred로 진행 중인 재발급을 대기하고, 완료 후 모든 요청을 새 토큰으로 재시도합니다.

synchronized는 스레드 간 동기화를 제공하지만 Kotlin 코루틴 환경에서는 비효율적입니다.
AtomicBoolean은 중복 호출을 방지할 수 있지만 비동기 완료를 기다리지 못합니다.
Kotlin 비동기 환경에 적합하고 명확한 제어가 가능한 Mutex를 선택했습니다.

결과적으로 다수의 요청에도 토큰 재발급이 중복 호출되지 않아 시스템 안정성을 확보했고, API 호출 횟수를 최소화해 네트워크 리소스 낭비도 줄였습니다.

왜 데이트피커를 직접 구현했는가

Android 기본 Picker는 커스터마이징이 제한적이어서 프로젝트에서 요구하는 맞춤형 테마와 동작 방식을 지원하기 어려웠습니다. AM/PM, 시간, 분 선택과 무한 스크롤 기능을 동시에 구현하면서 화면 공간을 효율적으로 사용해야 했습니다.

AS-IS — MutableState 단독 관리

스크롤과 상태 업데이트가 빈번해지면서 복잡성이 증가하고, 리컴포지션이 과도하게 유발됩니다.

TO-BE — snapshotFlow + LaunchedEffect

스크롤 상태를 추적하면서 항목이 변경될 때만 SelectedItem을 업데이트합니다.
중복 업데이트를 방지해 시스템 안정성을 확보합니다.

무한 스크롤은 전체 항목 개수를 크게 설정하는 방식과 Integer.MAX_VALUE를 사용하는 방식을 비교했고, Integer.MAX_VALUE를 선택해 성능 저하 없이 확장성을 유지하며 매끄러운 스크롤 동작을 구현했습니다. 상단/하단 페이드 효과는 Brush.verticalGradient를 활용했습니다.

왜 보상형 광고를 인터페이스로 추상화했는가

보상형 광고는 Activity 참조가 필요합니다. Domain/Data 레이어에서 Activity를 직접 참조하면 Clean Architecture 원칙에 위배되기 때문에 추상화가 필요했습니다.

RewardAdShower 인터페이스를 정의해 Activity 참조를 Presentation 레이어에서만 담당하도록 했습니다.
Domain과 Data 레이어는 인터페이스만 의존하므로 테스트 용이성과 유지보수성을 확보했습니다.

광고가 미리 로딩되어 있어도 startAd는 버튼 클릭 시 항상 호출해 서버 추적 정확도를 유지했습니다. 사용자가 대기하는 화면에서 광고를 시청하면 대기 없이 즉시 이어서 진행할 수 있도록 preloadAd를 활용했습니다.
