Background

유튜버 맛집 정보를 왜 지도로 모았는가

유튜버가 방문한 맛집 정보는 영상에 파편화되어 있습니다. 원하는 지역의 유튜버 맛집을 한 번에 지도로 탐색하거나 필터링하는 서비스가 없었습니다.

지도와 바텀시트를 결합해 유튜버별 필터링 기능을 제공했습니다.
맛집 상세 화면에서는 유튜브 영상을 직접 재생할 수 있도록 연결했습니다.

기획, 디자인, Android 개발까지 2인이 분담했으며 Android 개발은 전담했습니다. 1차 스프린트(2개월) 이후 Clean Architecture + Multi Module 구조로 전면 리팩토링했습니다.

Architecture

왜 단일 모듈에서 멀티 모듈로 전환했는가

1차 스프린트는 단일 모듈로 빠르게 개발했습니다. 하지만 단일 모듈은 변경 사항에 관계없이 전체 애플리케이션을 다시 빌드해야 했고, 파일 탐색이 어려워졌습니다. 추후 여러 개발자가 동시에 작업할 경우 코드 변경으로 인해 충돌이 발생하기 쉬운 구조였습니다.

AS-IS — 단일 모듈

변경 사항에 관계없이 전체 재빌드.
비즈니스 로직과 데이터 처리 코드가 UI 모듈에 혼재합니다.
동시 작업 시 충돌이 잦습니다.

TO-BE — Clean Architecture 기반 계층적 모듈

기능별 :feature, 계층별 :domain · :data, 공통 :core 모듈로 역할과 책임을 분리합니다.
:build-logic으로 Gradle 스크립트 중복을 줄이고 빌드 설정을 중앙 관리합니다.

단순히 모듈을 계층별로 분리하는 방법은 각 모듈 간의 의존성 관리가 어렵고 공통 코드 중복이 발생할 수 있었습니다. 기능 단위로만 모듈화하는 방식은 비즈니스 로직과 데이터 처리 코드가 UI 모듈에 혼재되는 문제가 있었습니다. 최종적으로 Clean Architecture를 기반으로 한 계층적 모듈화를 선택해 :core:network, :core:datastore 같은 공통 기능 모듈로 중복을 방지했습니다.

Technical Decisions

왜 그 기술을 선택했는가

왜 정적 페이징 대신 동적 페이징으로 무한 스크롤을 구현했는가

맛집 리스트에서 대량의 데이터를 끊김 없이 제공하려면 무한 스크롤이 필요했습니다. 정적 페이징 방식은 고정된 페이지 크기로 데이터를 가져오기 때문에 스크롤 위치에 따라 동적으로 데이터를 요청하기 어려웠고, 중복 데이터가 포함되는 문제도 간헐적으로 발생했습니다.

AS-IS — 정적 페이징

고정 페이지 크기로 데이터 요청.
스크롤 위치 기반 동적 로드가 어렵고, 중복 데이터가 발생합니다.

TO-BE — 동적 페이징 + 상태 관리

MutableStateFlow로 로딩 상태와 마지막 페이지 여부를 관리해 중복 요청을 방지합니다.
distinctBy로 중복 데이터를 제거해 데이터의 고유성을 보장합니다.

RecyclerView.OnScrollListener를 통해 이벤트 기반으로 데이터를 요청해 성능 저하를 최소화했습니다. 결과적으로 요청 횟수와 중복 데이터를 줄여 네트워크 및 서버 리소스를 절감했습니다.

카카오톡 공유와 CollapsingToolbarLayout 상세 화면

맛집 상세보기 화면은 CollapsingToolbarLayout으로 스크롤 시 헤더가 자연스럽게 접히는 유연한 UI를 구현했습니다. 카카오톡 공유는 KakaoShare SDK를 통해 맛집 정보를 친구에게 직접 공유할 수 있도록 제공했습니다.

검색 기능은 최근 검색어와 실시간 검색어를 함께 지원해 사용 편의성을 극대화했습니다. 온보딩은 ViewPager2를 활용해 사용자 친화적인 스와이프 방식으로 구성했습니다.
