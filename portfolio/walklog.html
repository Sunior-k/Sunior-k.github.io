Background

피트니스 앱 D30 리텐션이 5%인 이유

보상 기반 걷기 앱은 초기 참여를 끌어내는 데 효과적이지만, 보상이 유일한 동기가 되는 순간 보상의 힘이 약해지면 행동도 같이 사라집니다. 이것이 과잉 정당화 효과(Overjustification Effect)입니다.

보상이 유일한 이유가 되면, 보상이 식는 순간 행동도 같이 식습니다.
WalkLog는 이탈이 일어나는 4개 지점 각각에 다른 개입을 설계했습니다.
이탈 지점 현상 개입 전략
P1 — 진입 마찰 동기는 앱을 열어야 생기는데, 앱을 열 이유가 없으면 열지 않습니다. 걷기 예보 (피크아워 스마트 알림)
P2 — 첫 실패 목표를 한 번 놓치면 "어차피 오늘은 틀렸다"는 심리가 작동합니다. 스트릭 & 회복 시스템 (Grace Day)
P3 — 축적 무가치 쌓인 데이터가 자산이 아닌 숫자로만 남습니다. 주간 리포트 아카이브 & 월간 리캡 스토리
P4 — 알림 피로 고정 시간 알림은 개인화되지 않으면 소음이 됩니다. NDK 엔진 기반 peakHour 개인화 알림

Architecture

왜 모듈을 9개로 나눴는가

단일 모듈 구조에서는 어느 파일을 건드려도 전체를 다시 빌드하기 때문에, 기능이 늘어날수록 빌드 시간이 코드베이스 크기에 비례해 증가합니다. NiA(Now in Android) 패턴을 기반으로 feature · core 계층을 분리했습니다.

AS-IS — 단일 모듈

어느 파일을 수정해도 전체 재빌드.
Hilt · Compose 설정이 각 파일에 중복.
빌드 시간 ∝ 코드베이스 크기.

TO-BE — 멀티 모듈

feature:home만 수정하면 나머지는 재빌드하지 않습니다.
Convention Plugin이 모든 모듈에 설정을 통일 적용하며, 컴파일 타임에 단방향 의존성을 강제합니다.

:app ├── :feature:home ← 오늘의 걷기 대시보드 (Compose) ├── :feature:mission ← 미션 & 스트릭 (Compose) ├── :feature:history ← 월간 달력 (XML + ViewBinding) ├── :feature:report ← 주간 리포트 아카이브 (Compose) ├── :feature:recap ← 월간 리캡 스토리 (Compose) ├── :feature:forecast ← 피크아워 예보 BottomSheet (Compose) ├── :feature:settings ← 닉네임 & 테마 (XML + ViewBinding) ├── :feature:onboarding ← 4-step HorizontalPager (Compose) └── :core:* ├── :core:model ← 순수 Kotlin 도메인 모델 (Android 의존성 없음) ├── :core:data ← Repository 인터페이스 + 구현체 ├── :core:database ← Room 영속성 → core:model에만 의존 ├── :core:datastore ← DataStore 사용자 설정 ├── :core:domain ← UseCase (비즈니스 로직만) ├── :core:native ← C++ NDK 엔진 + LiteRT ActivityClassifier ├── :core:analytics ← CrashReporter 추상화 (Firebase 직접 노출 차단) ├── :core:common ← WalkLogDispatchers 주입, 공통 유틸 └── :benchmark ← Baseline Profile 생성 · Macrobenchmark
Technical Decisions

왜 그 기술을 선택했는가

왜 걷기 분석 로직을 C++로 짰는가

7일 × 24시간 배열의 시간대별 패턴 분석을 Kotlin에서 처리하면 분석 로직이 ViewModel에 섞이고, 코드 수정 시 의도치 않게 분석 로직을 건드릴 위험이 생깁니다.

AS-IS

Kotlin Flow로 배열을 순회.
정렬 · 평균 · 정규화 로직이 ViewModel에 섞입니다.

TO-BE

C++17로 분석 로직을 격리하고, JNI 단일 호출로 4개 지표를 반환합니다.
Kotlin은 결과만 소비합니다.

peakHour(지수 가중 argmax) · weeklyTrend(전반부/후반부 비율 정규화) · recoveryDifficulty(목표 달성률 평균) · streakRisk(현재 페이스 기반) 4개 지표를 계산하며, noexcept로 JNI 경계 예외 전파를 차단하고 JNI_ABORT로 읽기 전용 의도를 명시했습니다.

Health Connect 권한 상태를 왜 sealed class로 모델링했는가

Health Connect 권한 상태는 앱 미설치 / 설치됨 / 권한 없음 / 사용 가능 4단계로 나뉘며, 각 상태마다 UI 동작과 데이터 흐름이 다릅니다.

가용성 체크 로직을 feature 레이어까지 올리면 각 화면이 동일한 분기를 반복하게 됩니다.
Repository에서 sealed class로 상태를 모델링하면 UI는 상태만 소비하면 됩니다.

Android 14+에서는 activity-alias 두 개가 없으면 권한 다이얼로그 자체가 표시되지 않는데, 이는 공식 문서에도 명확히 기술되어 있지 않아 실기기 테스트에서 직접 발견했습니다.

Baseline Profile이 Full AOT보다 빠른 이유

처음에는 Full AOT가 더 빠를 것이라고 예상했지만 실측은 반대였습니다 — Full AOT 724.6ms, Baseline Profile 700.5ms. 모든 코드를 사전 컴파일하면 캐시에 올리는 비용이 JIT 오버헤드를 상회하기 때문입니다.

Baseline Profile의 핵심은 전체 AOT가 아닌 선별적 AOT입니다.
시작 경로만 AOT로 컴파일하고 나머지는 JIT에 맡기는 것이 더 빠릅니다.

:benchmark 모듈에서 StartupBaselineProfile + HomeBaselineProfile 두 경로를 수집했으며, ClassInit 4,141건 → 1,054건(−75%), JIT 이벤트 완전 제거를 확인했습니다. mapping.txt Crashlytics 자동 업로드로 난독화 후에도 스택 트레이스를 복원할 수 있습니다.

R8 Full Mode로 APK 53%를 줄인 방법

R8 Full Mode는 모듈 경계를 넘어 전체 코드베이스를 최적화 단위로 보기 때문에, 사용하지 않는 코드 제거와 클래스 병합이 모듈 내부가 아니라 전체 범위에서 동작합니다.

결과적으로 APK 66MB → 31MB(−53%), DEX 크기 −80.9%, DEX 파일 5개 → 2개를 달성했습니다. -keepattributes SourceFile,LineNumberTable을 유지해 난독화 이후에도 Crashlytics 스택 트레이스를 복원할 수 있도록 했습니다.

Challenges

풀기 어려웠던 것들

Glance 위젯 동기화 타이밍

Glance 위젯은 별도 프로세스에서 동작하기 때문에, WorkManager 15분 주기 갱신만으로는 앱 실행 직후에도 오래된 걸음 수가 표시됐습니다.

WorkManager 주기 갱신과 앱 포그라운드 진입 시 강제 업데이트를 조합해 해결했습니다. 위젯 프로세스 특성상 앱 상태를 직접 구독할 수 없기 때문에, 앱이 포그라운드로 돌아올 때 GlanceAppWidget.update()를 명시적으로 호출하도록 설계했습니다.

Compose + XML 하이브리드 다크모드 전환

Compose의 isSystemInDarkTheme()은 Compose 영역에만 적용되고, History · Settings 화면은 XML 기반이라 night 한정자 기반 시스템 테마를 따릅니다. 두 영역을 동시에 전환하려면 단일 진입점이 필요했습니다.

AppCompatDelegate.setDefaultNightMode()로 앱 전체 Configuration.uiMode를 변경하는 방법을 선택했고, distinctUntilChanged()로 중복 호출에 의한 불필요한 Activity Recreation을 억제했습니다.

JNI 경계에서의 C++ 예외 처리

JNI 경계를 넘는 C++ 예외는 정의되지 않은 동작을 일으키기 때문에, 분석 함수에 noexcept를 명시해 경계를 넘지 않도록 강제했습니다. 입력 배열은 읽기 전용이므로 GetFloatArrayElements에 JNI_ABORT를 사용해 네이티브 수정 내용이 원본 배열에 반영되지 않음을 명시했습니다.

Kotlin 쪽 require()로 사전 조건을 검증해 잘못된 입력이 JNI 레이어까지 내려오지 않도록 설계했으며, 방어 로직은 JNI 진입 전 Kotlin 레이어에서 담당하고 JNI 내부는 안전성 보장에만 집중합니다.

Baseline Profile — Full AOT보다 느린 이유 분석

Full AOT 적용 시 오히려 Baseline Profile보다 시작이 느렸는데(724.6ms vs 700.5ms), 모든 코드를 사전 컴파일하면 캐시에 올리는 비용이 JIT 오버헤드를 상회하기 때문입니다. 시작 경로를 선별적으로 AOT하는 Baseline Profile 방식이 더 효율적임을 실측으로 확인했습니다.
