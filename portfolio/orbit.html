Background

기존 알람 앱의 무엇이 문제였는가

기존 기상 알람 앱은 큰 소리와 강제 해제에 집중합니다. 알람을 끄는 것이 목표가 되면, 침대에서 일어날 이유는 사라집니다.

알람을 해제하는 게 목표가 되면, 일어나는 이유가 없어집니다.
Orbit은 미션을 수행하고 운세를 받는 경험으로 기상 자체를 동기화했습니다.

알람 종료 후 즉시 운세를 주는 대신, 흔들기 또는 클릭 미션을 완료해야만 운세를 획득할 수 있습니다. 미션 타입은 Firebase Remote Config로 실시간 제어해 A/B 테스트와 이벤트 운영이 가능합니다.

Architecture

왜 클린 아키텍처와 멀티 모듈을 함께 썼는가

기능이 복잡해질수록 사용자 경험 중심의 빠른 개선이 요구될 것으로 예상했기 때문에, 초기 설계 단계부터 유지보수성과 확장성을 함께 고려했습니다.

AS-IS — 단일 모듈

UI 로직, 비즈니스 로직, 데이터 처리가 혼재.
미션 기능 개선이 다른 기능에 영향을 줍니다.

TO-BE — Clean Architecture + Multi Module

Presentation · Domain · Data 3계층으로 책임을 분리합니다.
미션 개선은 feature:mission 내에서만 이루어지고, 다른 기능과 충돌하지 않습니다.

모듈 구조는 feature modules → :domain module → :data module의 단방향 의존성을 따르며, :core:designsystem, :core:ui, :core:network, :core:datastore, :core:security, :core:buildconfig 공통 모듈로 중복을 제거했습니다.

Technical Decisions

왜 그 기술을 선택했는가

왜 Firebase Remote Config로 미션 타입을 제어했는가

단순 랜덤 방식으로 미션을 결정하면 배포 후 비율을 조정하거나 A/B 테스트를 하기 위해 매번 앱을 다시 빌드해야 합니다. Firebase Remote Config를 활용해 미션 종류와 출현 여부를 실시간으로 조절할 수 있도록 설계했습니다.

AS-IS

미션 타입 하드코딩.
비율 조정마다 앱 재배포가 필요합니다.

TO-BE

RemoteConfig로 실시간 제어합니다.
Shake 29.3% / Tap 70.7% A/B 테스트를 배포 이후에도 운영했습니다.

Firebase Remote Config는 Android SDK에 종속된 라이브러리이기 때문에 Data Layer에서만 접근하도록 분리하고, Domain에서는 RemoteConfigRepository를 통해 추상화했습니다. ViewModel은 오직 UseCase를 통해 미션 타입만 받아 사용하므로 테스트 환경 교체가 용이합니다. 미션 타입은 sealed class MissionType으로 정의해 새로운 미션이 필요할 경우 타입만 추가하면 Domain과 Presentation만 보완하면 됩니다.

왜 운세 보상 이미지를 MediaStore로 저장했는가

운세 결과를 저장하거나 공유하고 싶다는 사용자 니즈를 반영해 보상 이미지를 갤러리에 저장하는 기능을 구현했습니다. Android 10 이상에서는 WRITE_EXTERNAL_STORAGE 권한 없이도 MediaStore를 통해 PNG 형식으로 저장할 수 있기 때문에 MediaStore를 선택했습니다.

설계는 ViewModel → Repository → LocalDataSource 구조로 구성했으며, 이미지 저장 처리를 UI 로직과 분리해 내부 로직에서 실패를 감지하고 로그만 처리하도록 했습니다. 처리 흐름은 Bitmap → ByteArray → OutputStream 순으로 구성했고, ByteArray 기반의 범용 처리 구조 덕분에 외부 이미지나 뷰 기반 캡처 이미지도 동일한 흐름으로 확장할 수 있습니다.
